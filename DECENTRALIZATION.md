# AuronQ decentralization model

AuronQ is designed so that consensus truth is not supplied by a website, explorer,
GitHub account, founder machine, seed node or API server.

## Full nodes are the network

Every AuronQ Desktop instance starts its own full node by default. A full node:

- stores and replays the canonical blockchain locally;
- validates blocks, proof-of-work, timestamps, difficulty, transactions, signatures,
  coinbase rules and UTXO spends itself;
- maintains and validates its own mempool;
- relays valid transactions and blocks to peers;
- learns public peers from other AuronQ peers and persists them locally;
- serves its own read-only Explorer from the same locally verified chain.

The local Explorer at `/explorer` is therefore not a central block explorer. It is
a view generated by that particular full node. If ten users run AuronQ Desktop,
there can be ten independent Explorers reading ten independently validated copies
of the same canonical AuronQ chain.

No Explorer response participates in consensus.

## No privileged first node

Seed peers are rendezvous hints only. They do not sign checkpoints, choose the
canonical chain, approve transactions or have special consensus weight.

A configured seed that repeatedly fails is pruned from the running peer set.
Peers learned from the P2P network are persisted and can replace the original
bootstrap set completely.

The canonical chain is selected by AuronQ consensus validation and cumulative
proof-of-work, not by the identity of the peer that supplied a block.

Turning off an original seed must therefore not invalidate or stop an already
connected network.

## Why a brand-new installation still needs bootstrap hints

A machine with no prior AuronQ state cannot discover an unknown peer address out
of nothing. Every permissionless P2P network needs some initial rendezvous
mechanism: bundled addresses, DNS seeds, a peer snapshot, local discovery, or
another out-of-band hint.

AuronQ treats these only as introductions. After contact, peer discovery is
native P2P gossip and the seed has no authority.

The long-term target is to bundle a diverse snapshot of independently operated
public nodes so a fresh release does not depend on the founder's machines.

## Public reachability and NAT

A full node behind NAT still validates its own chain, creates outbound P2P
connections and relays data through those connections. That increases redundancy
and removes trust in remote data sources.

It does not automatically become an inbound public server if the router or
firewall does not allow incoming connections. Public network capacity therefore
also requires independently operated reachable nodes.

Automatic NAT traversal/port mapping is a separate networking feature and must
never become a consensus dependency.

## Mining and security

Full nodes enforce the rules from the user's perspective and improve redundancy,
availability and censorship resistance. Proof-of-work security is increased by
miners performing AQM64 work.

Running a full node without mining does not increase AQM64 hash power. Running a
miner does.

## Mobile

AuronQ Mobile is currently a wallet/light client, not a full consensus node. It
keeps private keys locally and independently verifies the Mainnet header chain
from embedded genesis, including AQM64 proof-of-work, difficulty, timestamp and
previous-hash continuity. It remembers public peers learned from the P2P network
and can move away from its initial bootstrap peers.

Wallet balance, history and spendable UTXO state are not reconstructed locally
from every full block. Mobile therefore accepts that state only from replaceable
full nodes matching its independently verified header state and compares their
responses. Conflicting canonical wallet state fails closed; ordinary asynchronous
mempool differences are handled separately.

The mobile client must not be described as contributing the same full-state
validation as AuronQ Desktop until it implements complete block/UTXO validation
or a full-node mode.

Its bootstrap manifest is an optional freshness source. A bundled peer snapshot
is tried independently, and learned AuronQ peers are persisted by the app.

## Decentralization invariants

AuronQ development should preserve these rules:

1. Consensus validity must never depend on a founder-controlled server, domain,
   explorer, GitHub repository or API.
2. Seed nodes are replaceable discovery hints only.
3. A node must validate the data it accepts; peer identity is not trust.
4. The Explorer must read the node's own canonical chain.
5. Wallet private keys must remain local to the wallet.
6. Independent public nodes and miners must be able to join without permission.
7. Network operation after peer discovery must continue if the original seed
   machines disappear.
8. Bootstrap metadata must never alter Network ID, genesis or consensus rules.
9. Mobile/light clients must state clearly what they verify themselves and what
   they obtain from full nodes.
10. No single operator should be required for normal network operation.

## Long-term target

The engineering target is a self-sustaining AuronQ network consisting of many
independent full nodes, miners and wallets, where the original development
machines can be permanently powered off without affecting consensus, transaction
processing, local Explorer access or continued peer-to-peer operation.
