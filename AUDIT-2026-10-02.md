# AuronQ 1.7.0-rc2 — Internal pre-release audit (2026-10-02)

## Scope and status

This is an **internal engineering audit**, not an independent professional security audit. It reviewed consensus/issuance code, genesis validation, fork synchronization, P2P request handling, wallet/ML-DSA paths, AQM64 vectors, release/build paths and launch documentation.

Result: no known unresolved consensus-inflation/double-spend defect was found in the reviewed code, and the high-impact synchronization/remote-resource issues found during this review were fixed in rc2. Significant external-validation and long-term scalability risks remain and are listed below.

## Verification completed for rc2

- `go test ./...` — pass after rc2 hardening.
- `go vet ./...` — pass after rc2 hardening.
- race-enabled Go suite — pass during rc2 audit; repeat on the frozen release tree before tagging.
- Windows amd64 CLI/Desktop and Linux amd64 CLI cross-builds — successful during rc2 audit; rebuild after final documentation freeze and publish fresh hashes.
- ML-DSA-87 portable implementation interoperability — checked both directions against OpenSSL 3.5.5 ML-DSA-87; public-key derivation from the same 32-byte seed also matched.
- optional `legacycrypto` OpenSSL build path — repaired and tested.
- production-parameter AQM64 deterministic vector — present and executed.
- genesis production AQM64 path — exercised locally.

## Monetary-policy findings

- hard maximum: 21,000,000 AURQ (2,100,000,000,000,000 atoms);
- genesis founder allocation: 210,000 AURQ (1% of the hard cap);
- initial mined subsidy: 49.5 AURQ;
- halving interval: 210,000 mined blocks;
- transaction fees are transfers, not new issuance;
- normal block coinbase must equal `subsidy + fees`;
- mainnet coinbase maturity: 100 blocks.

Because subsidy halves by integer right shift, the exact terminal issuance is **20,999,999.979 AURQ**, i.e. 0.021 AURQ below the stated hard maximum. The 21,000,000 AURQ figure is therefore a cap, not an exact terminal mint amount.

## High-impact findings fixed in rc2

### 1. Fork-sync replay / fabricated-work DoS

Before rc2, ordinary synchronization could rebuild/rewrite the whole canonical chain for each batch, and a malicious competing peer could make an unvalidated target imply huge work before full validation, potentially forcing an expensive whole-chain replay.

rc2 changes normal extension sync to incremental `AddBlock` validation. For competing forks, downloaded headers/blocks must first pass version/algo/linkage, target, timestamp/MTP, Merkle and production AQM64 PoW envelope checks before their work is counted. A full UTXO replay/reorg is attempted only after the validated fork suffix exceeds local suffix work. Sync batches are bounded to 256 blocks.

### 2. Missing per-source request throttling

rc2 adds per-IP windows in addition to the existing global concurrency and body-size limits, including a tighter limiter on expensive block submissions. This reduces trivial single-source CPU/RAM exhaustion but does **not** protect against distributed botnets, large Sybil sets or upstream bandwidth attacks.

### 3. Incomplete network-identity commitment

The consensus fingerprint was expanded to commit additional fixed consensus-critical limits/rules, and Network ID now also commits protocol version. This intentionally changes the rc2 Network ID relative to earlier candidates even when the same genesis were reused; final mainnet must therefore be generated with rc2 or later frozen code.

### 4. Genesis validation hardening

Genesis now also runs basic transaction validation and explicitly requires the allocation transaction to have zero inputs and lock height zero, in addition to exact founder value/address/scheme and valid PoW checks.

### 5. Optional ML-DSA backend build break

The portable crypto source lacked the exclusion build tag for the optional legacy provider path. rc2 fixes the tag conflict; normal release builds remain portable/CGO-free.

### 6. First-run Desktop / release inconsistency

Desktop version is synchronized to rc2. If a verified final `network.json` is bundled beside `AuronQ-Desktop.exe`, a clean first launch copies it into the per-user configuration directory automatically; existing configuration is not overwritten. This enables a practical download/run/sync flow once public seeds exist.

### 7. Parser/release hardening

rc2 rejects trailing JSON values in request bodies, uses strict height parsing, tightens large block-response limits and aligns the Docker build with the Go 1.23 / CGO-free normal release path.

## Known limitations / unresolved external gates

These are not represented as solved by rc2:

- no independent professional consensus, cryptography or P2P security audit;
- no long-running hostile public mainnet-parameter test campaign;
- AQM64 is an AuronQ-specific composition; its GPU/FPGA/ASIC economics and time-memory tradeoffs have not been independently characterized;
- difficulty/timestamp behavior under adversarial low-hashrate launch conditions needs independent simulation/review;
- P2P still needs distributed DoS, eclipse/Sybil and stronger peer-quality/diversity testing; basic per-IP limiting is not sufficient against distributed attackers;
- synchronization is not yet a full headers-first architecture;
- startup currently replays canonical block files and revalidates chain state, including PoW; this is robust but will become slow as the chain grows unless safe snapshot/index acceleration is added;
- canonical storage uses individual block files and has not been stress-tested at multi-year production scale;
- no formal verification;
- public release binaries are not code-signed;
- byte-for-byte reproducible builds across independent builders have not yet been demonstrated;
- fuzzing and malicious-network load testing remain incomplete;
- the production end-to-end mining smoke test is probabilistic and did not find a post-genesis block within the audit session's bounded run; deterministic consensus integration tests cover the transaction/block path, but a long production-parameter smoke run should still be performed as an additional operational check.

## Launch interpretation

rc2 is technically capable of creating and operating a public permissionless mainnet. That statement means the software has the necessary node, consensus, wallet, mining, persistence and P2P mechanics; it is **not** a claim that the network is proven secure for material financial value.

If mainnet is launched before the unresolved independent gates above, the release must prominently preserve that status and the exact source/network/checksum record so users can make an informed decision.
